# Vision Pipeline: Bulk Content Generation from Binaries

Use this when generating content for 50+ binary files in a Webflow CMS collection where Claude must SEE each file to produce the output. **Canonical case: alt text for multi-image fields** (set-of-images, gallery, carousel) — every image in the array needs its own unique alt, generated by looking at the image. Also covers single-image fields (main-image, thumbnail), image categorization, PDF summarization, screenshot QA — anything where the output is derived from a binary.

For the eight base principles, see parent `SKILL.md`. For the push mechanics in step 4, see `references/push-pattern.md`. For the multi-image field PATCH schema specifically, see `references/push-pattern.md#patching-multi-image-fields`. For the wall this pattern is designed around, see `references/webflow-gotchas.md#8-the-32mb-request-cap-when-reading-binaries-in-session`.

## The four-phase pipeline

Every vision-batch job follows the same shape:

1. **Prep** — Download binaries to the project folder. Normalize formats and sizes.
2. **Vision** — Claude reads each binary and produces the content.
3. **Verify** — Review the generated content as a markdown report. Approve.
4. **Push** — PATCH the field(s) back to Webflow. Bulk publish at the end.

Steps 1, 3, 4 are mechanical. Step 2 is the architectural decision — three patterns, choose by batch size.

## Step 1: Prep

Pull binaries from Webflow into the project folder. Never `/tmp` — subagents can't reach `/tmp` in this harness, and project folder paths are version-controllable for review.

```bash
mkdir -p ./batch/binaries

# Pull image URLs from the collection (or your task source)
# ... your code to write batch/tasks.json with {url, fileId, item_slug, ...}

# Download all binaries
python3 -c "
import json, urllib.request, os
tasks = json.load(open('batch/tasks.json'))
for t in tasks:
    out = f'batch/binaries/{t[\"fileId\"]}.bin'
    if os.path.exists(out): continue
    urllib.request.urlretrieve(t['url'], out)
"
```

### Format normalization (images only)

Webflow serves AVIF with `.jpg` extensions. Detect by magic bytes, not extension:

```bash
for f in batch/binaries/*.bin; do
  magic=$(head -c 12 "$f" | xxd -p)
  case "$magic" in
    *66747970617669*) mv "$f" "${f%.bin}.avif" ;;  # AVIF
    ffd8ff*)          mv "$f" "${f%.bin}.jpg"  ;;  # JPEG
    89504e47*)        mv "$f" "${f%.bin}.png"  ;;  # PNG
  esac
done

# Convert AVIF → JPG so the Read tool can decode them
for f in batch/binaries/*.avif; do
  sips -s format jpeg "$f" --out "${f%.avif}.jpg" >/dev/null
  rm "$f"
done
```

### Size normalization

Anthropic's vision API caps each image at 2000px on the longest edge for multi-image turns. One oversize image will reject the whole turn. Resize all in place — `sips -Z` only shrinks, never upscales:

```bash
sips -Z 2000 batch/binaries/*.jpg >/dev/null
```

After prep, you should have `batch/binaries/<fileId>.jpg` for every task and a `batch/tasks.json` describing what to do with each.

## Step 2: Vision — three patterns

The constraint is the 32MB per-request cap (`references/webflow-gotchas.md#8`). When Claude Reads a binary in-session, the bytes embed permanently into conversation history. Cumulative history is what hits the wall, not any single Read.

| Batch size | Pattern | Why |
|---|---|---|
| < 100 items | **A. Inline** (one per turn) | Same chat. Peaks ~15MB at item 100. Safe. |
| 100–800 items | **B. Parallel subagents** | Each subagent gets a fresh 32MB. 4 subagents × 200 each = 800 capacity. |
| > 800 items, OR async preferred | **C. Handoff to new chat** | See `session-handoff.md`. Manual, but simple and robust at any scale. |

Pick by item count. If unsure, prefer the next-larger pattern — overkill costs nothing, undershooting wastes the partial run.

### Pattern A — Inline (small batches)

Process one item per turn. Read the binary, produce the output, write to `batch/results.json` immediately, move to next item. Resume-safe via a progress file.

```python
import json, os
PROGRESS = "batch/progress.txt"
RESULTS  = "batch/results.json"

done = set()
if os.path.exists(PROGRESS):
    done = set(open(PROGRESS).read().splitlines())

results = json.load(open(RESULTS)) if os.path.exists(RESULTS) else {}
tasks = json.load(open("batch/tasks.json"))
todo = [t for t in tasks if t["fileId"] not in done]
print(f"{len(todo)} of {len(tasks)} remaining")
```

Then in the chat: Read the binary file for the next task, generate the output, append to `results.json` + `progress.txt`. One Read per turn keeps the wall predictable.

### Pattern B — Parallel subagents (medium batches)

Main session does prep (no binaries touched). Then dispatches N subagents in ONE message (multiple Agent tool calls = parallel execution). Each subagent processes its own chunk in its own private context.

```python
# Split tasks into N chunks BEFORE dispatching
import json, math
tasks = json.load(open("batch/tasks.json"))
N = 4  # subagent count
chunk_size = math.ceil(len(tasks) / N)
for i in range(N):
    chunk = tasks[i*chunk_size:(i+1)*chunk_size]
    json.dump(chunk, open(f"batch/chunk_{i}.json", "w"), indent=2)
```

Then in main chat, dispatch all subagents in one message:

```
Agent #0: process batch/chunk_0.json → write batch/subagent_results_0.json
Agent #1: process batch/chunk_1.json → write batch/subagent_results_1.json
Agent #2: process batch/chunk_2.json → write batch/subagent_results_2.json
Agent #3: process batch/chunk_3.json → write batch/subagent_results_3.json
```

Each subagent's brief should be self-contained:

```
You are processing a vision-batch chunk for a Webflow CMS update.

INPUT:  batch/chunk_<N>.json — array of tasks, each with {fileId, item_slug, binary_path, context}
OUTPUT: batch/subagent_results_<N>.json — array of {fileId, output} objects

For each task:
1. Read the binary at task.binary_path
2. Generate the output per the prompt template below
3. Append to your output file IMMEDIATELY (resume-safe)

Constraints: <task-specific, e.g., alt text ≤125 chars, no "image of..." prefix>

Return a one-line summary: "N/N done, written to batch/subagent_results_<N>.json"
Do NOT include the generated content in your final message — it's in the file.
```

After all subagents return, merge:

```bash
python3 -c "
import json, glob
merged = {}
for f in sorted(glob.glob('batch/subagent_results_*.json')):
    for item in json.load(open(f)):
        merged[item['fileId']] = item['output']
json.dump(merged, open('batch/results.json', 'w'), indent=2)
print(f'Merged {len(merged)} items')
"
```

Why subagents instead of inline: each gets a fresh 32MB. Why text-only summary back to parent: parent never sees the binaries. Why one chunk per subagent: avoids race conditions on the output file.

**Caveat:** subagents block the parent during their run. If the batch is large enough that you'd rather step away, use Pattern C.

### Pattern C — Handoff to new chat (large batches OR async)

See `references/session-handoff.md` for the full pattern. Brief recap:

1. Skill writes `.handoff/task.md` (the worker's brief) and initializes `.handoff/progress.md`
2. Skill prints copy-paste instructions for the user to open a new chat with a recommended model
3. Worker chat reads `task.md`, processes binaries, writes `batch/results.json`, updates `progress.md` periodically
4. User returns to original chat and types `done`
5. Original chat verifies `progress.md` is COMPLETE, reads `results.json`, continues to step 3

This pattern works at any scale (the worker chat can use subagents internally, or further hand off if needed). It's the only path that lets the user step away while the batch runs.

## Step 3: Verify

Generate a markdown report from `batch/results.json` and show the user before any push. The report should make it trivial to spot bad outputs at a glance.

```python
import json
results = json.load(open("batch/results.json"))
tasks = {t["fileId"]: t for t in json.load(open("batch/tasks.json"))}

with open("batch/verification-report.md", "w") as f:
    f.write("# Vision batch — verification\n\n")
    f.write(f"Generated: {len(results)} of {len(tasks)} items\n\n")
    f.write("| Slug | fileId | Output | Length |\n|---|---|---|---:|\n")
    for fid, output in results.items():
        slug = tasks.get(fid, {}).get("item_slug", "?")
        f.write(f"| {slug} | {fid[:8]} | {output} | {len(output)} |\n")
```

Show the user. Get explicit approval. Do not push without it.

## Step 4: Push

Use the multi-image field PATCH pattern from `references/push-pattern.md#patching-multi-image-fields`. Critical: spread `**img` to preserve `fileId` and `url` on each existing image; only the target field (e.g., `alt`) changes.

After all PATCHes, one bulk publish:

```python
# POST /v2/collections/{id}/items/publish — up to 100 IDs per call
import json, urllib.request
results = json.load(open("batch/results.json"))
item_ids = list({tasks[fid]["item_id"] for fid in results})
for batch_start in range(0, len(item_ids), 100):
    chunk = item_ids[batch_start:batch_start + 100]
    payload = {"itemIds": chunk}
    # ... POST to publish endpoint
```

## When NOT to use this pattern

- **Single-binary jobs.** Open the item in the Webflow editor and edit the field manually.
- **Mixed binary types in one batch.** Split into multiple pipelines per type — different prep, different prompts.
- **Output isn't binary-derived.** Use `references/fix-pass-pattern.md` for text-only sweeps.
- **Re-uploading the binaries themselves.** This pattern only updates fields on existing image objects. For new uploads, use Webflow's `/assets/upload` endpoint (not covered by this skill yet).
